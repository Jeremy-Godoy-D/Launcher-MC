# Mundos: bloqueo de sesión nativo durante cambios revisados

Fuente `08578dbc35d7337202703d968b478c065944d826`. Etapa 5 activa; K11/K12/K21 permanecen pendientes. Este bloque añade protección Windows a los recorridos revisados de mundos, sin configurar Microsoft ni cambiar producción.

## Comportamiento

Electron utiliza el Koffi ya empaquetado para abrir `session.lock` sin truncarlo y adquirir un bloqueo exclusivo del primer byte con LockFile. Ese rango se solapa con el bloqueo Java NIO de una sesión. La mera existencia de un archivo antiguo no se considera una partida abierta. Se rechazan enlaces, hardlinks, directorios y cambios de identidad del mundo/control; los fallos de acceso o de proveedor cierran la operación. No se expone un IPC nuevo ni se abre un archivo elegido por el renderer sin pasar por la revisión/autoridad Native existente.

El bloqueo se mantiene durante los cambios de metadatos, datapacks, copia/exportación y publicación/restauración de chunks, con verificaciones antes de escribir y liberación en finally. Una revisión no crea archivos; una operación de chunks obsoleta tampoco. Al confirmar un cambio sobre un mundo propio sin control se puede crear un `session.lock` vacío, que permanece sin alterar los datos del mundo. Los errores de sesión activa reutilizan el mensaje recuperable de cerrar la partida.

El archivo de control raíz se excluye de las instantáneas/copia/exportación de carpetas; los demás consumidores de readFolderSnapshot conservan su comportamiento. Esto permite verificar/copiar el mundo mientras su control está bloqueado y evita propagar un control antiguo. La retirada conserva el archivo original junto al resto del mundo en su respaldo. Las fuentes externas de importación no reciben un control nuevo: si no existe, se vuelve a comprobar en cada verificación de la instantánea; su contenido permanece de solo lectura. Importar un ZIP no implica una sesión activa sobre sus archivos comprimidos. Retirar solo un enlace propio no modifica el mundo compartido ni necesita bloquearlo.

Windows impide renombrar una carpeta mientras está abierto un archivo hijo. Por eso la retirada verifica y libera nuestro handle inmediatamente antes del rename: si un juego obtiene el control en ese intervalo, el propio movimiento falla conservando el origen. La prueba Native pausa exactamente ese rename, abre una sesión Java real y confirma tanto el rechazo como el reintento posterior. No se sustituye esta garantía por borrar el mundo o usar una copia destructiva entre discos.

La semántica utilizada procede de [LockFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfile), [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) y [FileChannel.tryLock](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/channels/FileChannel.html). Las pruebas usan el JDK 17 instalado, sin descargar ni cambiar el Java del equipo. La [imagen Windows de GitHub](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md) documenta JAVA_HOME_17_X64; el helper utiliza esa variable o JAVA_HOME/Java existente.
